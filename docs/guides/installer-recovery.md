# Installer ownership and recovery

Use an installer from 0.5.1 or newer to preserve foreign links and completely
resynchronize a selected asset set. This changes neither the version pin nor
project documents. Back up local edits before switching a checkout; do not use
force or reset to discard them as part of this procedure.

## Ownership boundary

Cortex-created skill and Markdown-rule links point directly into the selected
clone's `skills/` or `rules/` directory. Ownership is checked using literal path
components, not a substring or regular expression. A similar directory prefix,
lexical traversal or an unrelated target does not grant ownership. Existing real
skill directories and command files are preserved.

Cursor-generated rules are regular `.mdc` files whose first line is exactly
`<!-- generated by cortex -->`. The marker identifies files Cortex may refresh
or remove. A marker quoted later in user content does not identify a generated
file. A symbolic link is never followed for a generated-file write. Keep a custom
Cursor rule without the marker if it should remain user-owned.

Install and update prune obsolete managed links and generated rule files before
syncing the selected source assets. A Rule that changes from global to on-demand
also loses its managed global installation. Foreign files and links are preserved;
reported conflicts remain for the user to resolve, rather than being overwritten.
These operations are not transactional and do not promise concurrent-writer safety.

## Roll back assets using a retained fixed installer

Start from a clean canonical clone containing the 0.5.1-or-newer installer. Obtain
the intended release tag before switching if the clone is shallow. Retain the fixed
installer outside the clone: checking out an older tag also changes `bin/cortex`,
so running that older copy would reintroduce the old ownership and cleanup defects.

For the default installation path, the parent directory already exists:

```sh
cortex_checkout="$HOME/.local/share/ai-cortex"
cortex_manager_dir=$(mktemp -d "$HOME/.local/share/cortex-manager.XXXXXX")
cp "$cortex_checkout/bin/cortex" "$cortex_manager_dir/cortex"
git -C "$cortex_checkout" fetch --tags origin
git -C "$cortex_checkout" checkout --detach v0.4.0
CORTEX_HOME="$cortex_checkout" sh "$cortex_manager_dir/cortex" install
```

Change `cortex_checkout` to the actual clone when using a custom location. Verify
that no broken managed links remain and that installed skills and global rules
match the selected version. `cortex status` can show counts; it does not certify
runtime discovery inside an IDE.

Keep the retained manager until returning to 0.5.1 or newer. The command link still
points at the selected clone, including its older installer; use the retained
manager explicitly for further resynchronization or uninstall while pinned there:

```sh
CORTEX_HOME="$cortex_checkout" sh "$cortex_manager_dir/cortex" uninstall
```

Do not run `cortex update` to retain a release pin: it fetches the remote default
branch and resets the canonical clone to it. Re-select a release explicitly when
that is the intended behavior. Uninstall keeps the source clone by default.

An asset rollback does not undo edits to consuming projects or remote pages.
Recover those through their own backups and authoritative records. Do not merge
old pre-rewrite history into the rewritten main branch.

## Verification

`python3 scripts/test-cortex-installer.py` executes the real POSIX entry point
against small isolated asset sets, temporary homes and local Git repositories.
It covers user-owned files/links, prefix and traversal boundaries, generated-file
markers, repeated installation, source-revision rollback, pruning and dirty-update
refusal. CI executes it on Linux and macOS without fetching release tags or using
an external network. These are installer integration tests, not IDE invocation tests.
