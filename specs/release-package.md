# Release Package Schema

> **Data contract**: defines the release package structure shared across the prepare, publish and announce stages

## 1. Position and scope

A Release Package is the auditable carrier for one release candidate, holding the version, the commit range, the release materials, the quality evidence and the stage status in a single object.

In scope: preparing a version, executing a release, generating release communication material, and carrying release evidence between stages.

Out of scope: a particular platform's upload API, deployment protocols, media generation algorithms, and channel delivery formats.

## 2. Mental model

A Release Package answers six questions. Decision: is a new version warranted? Identity: which project and which commit range? Versions: which version domains change? Changes: what changed for users and technically? Artifacts: what materials exist? State: which stage is it in, and on what evidence?

## 5. Body structure contract

### 5.1 Top-level fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `schema_version` | string | yes | The Release Package schema version |
| `project` | string | yes | Project identifier |
| `decision` | enum | yes | `release` / `none` |
| `version` | string | conditional | Required when `decision=release`; SemVer with no `v` prefix |
| `release_channel` | string | conditional | Required when `decision=release`, such as `alpha` / `beta` / `rc` / `stable` |
| `version_source` | string | conditional | Required when `decision=release`; the canonical source path of the product version |
| `version_domains` | object | yes | The independent version domains — product, build, API, protocol and the like — and the action taken on each |
| `commit` | string | yes | The full commit SHA the release corresponds to |
| `range` | string | yes | The git range from the previous release to this commit |
| `status` | enum | yes | `draft` / `not_required` / `ready` / `published` / `announced` |
| `change_items` | array | conditional | Required when `decision=release`; the structured changes reused by materials, video and announcements |
| `artifacts` | object | yes | Index of release materials |
| `checks` | array | yes | The gates that ran, and their results |
| `publication` | object | conditional | Required once `status` is `published` or later |
| `communication` | object | conditional | Required when `status` is `announced` |

### 5.2 Artifact entry

Every entry carries at least `path`, `kind`, `audience`, `required`, `status` and `source`. `kind` may be `changelog`, `release_notes`, `customer_notes`, `manifest`, `sbom`, `checksums`, `build`, `video` or `other`; `status` may be `planned`, `present`, `skipped`, `unavailable` or `failed`. `audience` distinguishes at least `technical`, `operator`, `customer` and `internal`; `source` points at the change items or the authoritative file the material came from. Material generated by a skill also carries `producer`, recording at least the local skill's name, version and origin classification: an AI Cortex original skill uses `origin: native`, an externally derived local copy uses `origin: vendored-derived` together with `source_registry`. `video` is an optional material by default; a required artifact satisfies readiness only at `status=present`.

### 5.3 Version domain entry

Every version domain carries at least `current`, `source` and `action` (`bump` / `preserve` / `derive`). Only the product version domain takes part in a SemVer bump by default; build, API, protocol, data format and prompt versions must not be bumped in lockstep merely to keep the numbers aligned.

### 5.4 Change item

Every change carries at least a stable `id`, a `kind` (`feature` / `improvement` / `fix` / `breaking` / `internal`), `summary`, `user_impact`, `sources` and `audiences`. Optional fields include `module`, multilingual `title` and `body`, `migration`, `highlight` and `media`. The technical changelog, the user-facing release notes, the video and the announcement all derive from the same set of change items, rather than copying from each other and each rewriting the facts.

### 5.5 Check entry

Every check carries at least `name`, `status` (`passed` / `failed` / `skipped`), `evidence` and `required`. The package may become `ready` only when every required check has `status=passed` and evidence establishing that its declared scope executed successfully. A skipped required check blocks readiness even when its skip reason is recorded.

For tests, a successful command exit alone does not establish execution; zero executed cases, all-skipped cases, or unverified execution cannot be recorded as `passed`. Evidence may use framework counts or output identifying completed checks and their outcomes; no additional report format is required. When execution cannot be verified and no failure is established, record the check as `skipped` with the missing evidence; retain `failed` when a build, environment or test failure is established. An unverified required check keeps the package at `draft`; an optional check does not block readiness, but its actual outcome and evidence gap remain visible. When `decision=none`, the status must be `not_required` and a publication result must not be created.

### 5.6 Publication entry

`publication` carries at least the target commit, tag, provider, per-step status and the success receipt. Per-step status uses `not_started` / `partially_applied` / `complete` / `failed`, covering version sync, the release commit, validation, tagging, build and package, and provider publish. That status exists for failure recovery, and a final boolean must not paper over the intermediate facts.

### 5.7 Communication entry

`communication` carries at least the target audience, a required/optional marker per channel, the delivery status and the receipt. The top-level status moves from `published` to `announced` only when at least one channel succeeded and every required channel succeeded. A failed optional channel must be retained, but does not block that transition.

### 5.8 Version 2 staged release contract

Sections 5.1–5.7 define the existing 1.x contract and retain their meanings. A
2.0.0 package is a separate, explicitly selected contract; never represent it as
an executable 1.x `ready` package with an optional sidecar. Consumers MUST
validate the supported schema before any mutation. If a legacy consumer's
rejection cannot be verified, do not send it a 2.x package or enable that path.

A 2.x package records one release and its authoritative history. It carries:

| Field | Required content |
| --- | --- |
| `schema_version`, `project`, `release_id` | Explicit schema and stable project/release identities |
| `release_version` | Project-sourced version and scheme, or an explicitly unknown planned value; do not derive it from build numbering |
| `change_items` | Changes with their sources and audiences, as in 5.4 |
| `candidates` | Candidate IDs, source revisions, build identities, artifact identities and locations, and observed evidence; unknown values remain unknown |
| `targets` | Each target's required/optional status, selected candidate/artifacts, per-stage outcomes, actual delivered identities and publication evidence |
| `checks` | Candidate, target, stage, check, required status, actual outcome and evidence; checks are not inherited by another candidate or target |
| `exceptions` | Approver, candidate, target, check, scope, rationale and evidence for a project-permitted internal check; never overwrite its actual outcome |
| `attempts` | Intended action, authorization scope, operation identity, observed outcome and receipts, including unknown and partial outcomes |
| `communication` | Per-destination results and receipts, independent of product delivery |

The 2.0.0 serialization uses JSON-compatible objects and arrays. Every top-level
field above is present, including empty arrays when no observations exist. Each
record below has the listed fields; identifiers are nonempty strings unique in
their collection, and evidence is a nonempty reference when an outcome is claimed.

| Record | Fields and validation |
| --- | --- |
| `release_version` | Object with `value`, `scheme`, `source`; a planned unknown value is null and is never reported as observed. |
| Candidate | `id`, `source_revision`, `build_identity`, `artifacts`; each artifact has `id`, `location`, `identity` and `evidence`. Unknown build/output values remain null; an actual artifact requires identity and evidence. |
| Target | `id`, `required` boolean, `candidate_id`, `artifact_ids`, `status`, `delivered_artifacts`, `evidence`; status is `pending`, `complete`, `failed` or `unknown`. A complete target requires selected identities, actual delivered identities and supporting evidence. |
| Check | `id`, `candidate_id`, `target_id`, `stage`, `required` boolean, `origin`, `status`, `evidence`; stage identifies the action or completion it gates. Status is `pending`, `passed`, `failed` or `unexecuted`; a pass requires execution evidence. |
| Exception | `candidate_id`, `target_id`, `check_id`, `scope`, `approver`, `rationale`, `evidence`; all fields are required and must match the specific check and action. |
| Attempt | `id`, `target_id`, `action`, `authorization_scope`, `outcome`, `operation_id`, `evidence`; outcome is `intent`, `complete`, `failed`, `partial` or `unknown`. An intent exists before a remote action and an observed completion requires evidence. |
| Delivered artifact | `candidate_artifact_id`, `identity`, `relationship`, `evidence`; relationship is `unchanged` or `transformed` and is backed by evidence. Unknown or contradictory relations cannot complete the target. |

Candidate, target, check, exception and artifact references MUST resolve to the
same release, candidate and target scope. A status or reference not described by
the selected schema is rejected before mutation. The project determines which
checks gate each operation and what verification a transformation requires.
Absence of a policy for a failed check never implies that it can be waived.

Preparation records prerequisites and planned later checks separately. Upload
may occur when its applicable earlier prerequisites are met and authorized; it
does not make a later required check pass. The selected candidate must satisfy
its applicable checks or a valid scoped exception. Missing authorization,
unverified or mismatched identity and provider-enforced blockers cannot be
waived. If the delivered output differs, preserve its relation to the candidate
and verify it under the applicable project and provider rules.

A target is complete only with its applicable delivery evidence. Overall
publication requires at least one completed target and every required target to
complete; optional failures remain visible. Announcement eligibility is scoped
to verified published targets. Before a repeat write, reconcile complete
relevant provider state: reuse a confirmed result, retry a confirmed absent
action only under its existing authorization, and stop on unknown or conflict.
Persist attempt intent before remote mutation, and prevent conflicting writers
using a verified single-writer or compare-and-swap boundary; otherwise stop.
No credentials belong in the package.

## 6. Anti-patterns

- ❌ Three skills each defining their own version, artifact or status fields
- ❌ Deciding SemVer from commit prefixes or commit counts alone, without checking the actual user impact
- ❌ Bumping independent version domains such as API, build or prompt in lockstep just to keep the numbers aligned
- ❌ Using `published` to mean a local tag was created and nothing more
- ❌ Treating the optional `video` material as a release blocker by default
- ❌ Marking a package `ready` with a skipped required check, or declaring tests passed from exit code zero without evidence that the selected scope executed successfully
- ❌ Omitting the commit SHA or the git range, leaving the contents untraceable
- ❌ Stuffing a channel's proprietary message block straight into the Release Package

## 7. Examples

### 7.1 A releasable package

```yaml
schema_version: 1.2.1
project: example-service
decision: release
version: 2.4.0
release_channel: stable
version_source: package.json
version_domains:
  product: {current: 2.3.1, source: package.json, action: bump}
  api: {current: 1.8.0, source: api/openapi.yaml, action: preserve}
commit: 0123456789abcdef0123456789abcdef01234567
range: v2.3.1..0123456
status: ready
change_items:
  - id: export-filter
    kind: feature
    summary: Add saved filters to exports
    user_impact: Users can reuse filters when exporting reports
    sources: [abc1234]
    audiences: [technical, customer]
artifacts:
  changelog: {kind: changelog, audience: technical, path: CHANGELOG.md, required: true, status: present, source: change_items}
  release_notes: {kind: release_notes, audience: customer, path: RELEASE_NOTES.md, required: true, status: present, source: change_items}
  video: {kind: video, audience: customer, path: null, required: false, status: skipped, source: change_items, producer: {skill: changelog-video, version: 1.0.1, origin: vendored-derived, source_registry: skills/SOURCES.yaml}}
checks:
  - {name: tests, status: passed, evidence: "artifacts/pytest.log: 24 passed, 0 failed, 0 skipped", required: true}
```

### 7.2 No new version warranted

```yaml
schema_version: 1.2.1
project: example-service
decision: none
version_domains:
  product: {current: 2.3.1, source: package.json, action: preserve}
commit: 0123456789abcdef0123456789abcdef01234567
range: v2.3.1..0123456
status: not_required
artifacts: {}
checks: []
```

### 7.3 The optional video capability is missing

```yaml
artifacts:
  video: {kind: video, audience: customer, path: null, required: false, status: unavailable, source: change_items}
checks:
  - {name: changelog-video, status: skipped, evidence: "vendored local skill is not installed", required: false}
```

## 8. Relationship to other assets

- `prepare-release` constructs and validates the Release Package.
- `changelog-video` consumes the confirmed change items and returns the optional video artifact along with a check result.
- `publish-release` consumes a `ready` package and writes the publication result.
- `announce-release` consumes a `published` package and writes the communication result.
- [Universal Notification](./universal-notification.md) defines the notification structure; the channel delivery flow is defined by [INP](../protocols/im-notification-delivery.md).
