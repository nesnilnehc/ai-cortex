# Deploy an existing artifact

1. **Resolve the release.** Read the project's local entry point and its producer or release record. Match the requested build or version, source revision when requested, and each required artifact. Resolve mutable tags and labels to immutable references or trusted checksums. Keep the identities for a multi-artifact release together and check platform compatibility.
2. **Plan the local handoff.** Use an authorized installed or connected tool for each required operation. Prefer the local project entry point when it can consume those exact artifacts without building, publishing, or targeting a different runtime. For a package or binary behind systemd, pm2, or supervisord, require the project's supported install or switch operation, its association with the running unit or process, and an identity check. A restart alone can leave the previous executable selected. When a required capability or project handoff is missing, describe the gap before mutating the target.
3. **Retrieve and verify.** After binding the target and showing the plan, pull or read only the resolved artifacts. Compare their digests or checksums with the producer record, trusted repository metadata, or an explicit immutable reference supplied by the user. If the artifact is missing or its identity is uncertain, stop before deployment. Creating a replacement belongs to the project's artifact delivery workflow when separately authorized.
4. **Deploy and inspect.** Run the scoped, build-free handoff with the project's startup and migration gates intact. Use the shared verification and report in [the skill workflow](../SKILL.md#run-commands-and-verify-results). Readiness and observed runtime identity are both required.

## Docker Compose

### Bind the effective stack before changing it

- Resolve the actual Docker endpoint from the invocation and its effective context or host, including CLI flags, environment overrides, and Docker Desktop's local engine. A context name or local client alone is insufficient. Identify the Compose project name, working or project directory, ordered Compose files, active profiles, environment-file references, named services, replica counts, and dependencies. Confirm the same engine and configuration apply to plan inspection, build or pull, start, and verification.
- Determine which services and startup or migration jobs the command can create, start, or replace. Keep that set within the authorized change. A scoped command includes the intended services and their required dependencies. Use `--no-deps` only when their state is already verified and the project supports omitting dependency startup without bypassing a gate. Prefer a verified wrapper if it preserves the expected scope and order.
- Inspect the merged configuration. Use `docker compose config --services` or `--images` when those fields suffice. To inspect more fields, filter the effective configuration locally to the project name, selected services, images, build presence, mounts, startup commands, and dependencies needed for the decision. Keep raw environment values, secret data, and credential-bearing arguments out of output and reports.
- Check effective mounts, entry points, and startup commands for anything that changes the application executed from the selected build or image. A bind mount over application files can change the running code while preserving the image ID. Verify which contents the process will use or resolve the mismatch before deployment. Preserve data mounts and other settings outside the agreed change.

### Update the selected services

For an existing image, use a documented image parameter or a temporary local override that changes only the authorized image references. Set an immutable reference for every selected release image, including any job that uses one. Retain the original ordered Compose inputs and append the override. Reinspect the merged images, mounts and scope, then pull only the resolved images into the bound engine. Confirm that every service the invocation can start has its intended image locally. Use the bound Compose invocation with `up -d --no-build --pull never <authorized-service> ...`, or an equivalent documented wrapper. If a needed image or dependency is outside the plan, stop and resolve it first. Keep the effective configuration available for verification and remove only a temporary override created for this run when it is no longer needed.

For a source image, confirm what the Docker build context consumes and which image the selected services will run. If a host build produces files that the image build packages, verify both steps and their handoff. For a combined build and deployment, establish that the command stops on a build failure before touching the services it updates, then resolve the actual resulting image ID. An image-only Compose configuration cannot build the current source.

### Verify the update

Use the same engine and effective Compose configuration. Enumerate all expected service instances, including stopped containers when checking one-shot jobs or diagnosing failures. Inspect each selected container's image ID and compare it with the intended image ID resolved locally for the same platform. Use startup and mount evidence or the application's build identity to establish what actually runs. Check the project's readiness with a finite deadline. For a required one-shot job, establish that the observed run corresponds to this deployment and has the expected image and terminal exit state. A prior successful container record alone does not prove that a job ran this time. If the project expressly reuses a prior completed gate, verify the evidence required by that policy and report the reuse.
