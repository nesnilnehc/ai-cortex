# Deploy an existing artifact

1. **Resolve the artifact.** Read the project's local deployment entry point and producer record. Identify the intended build or version, source revision when requested, and every required artifact. Resolve tags and versions to immutable references or checksums. For a multi-image release, use the identities from one release record. Check that the artifact platform is supported by the local runtime.
2. **Select the local deployment command.** Prefer a project-owned entry point that accepts the resolved artifacts. Use installed or connected tools that support the required read, pull, deploy, and inspect operations. If none supports a required operation, report the missing capability. Keep the deployment confined to the selected local target and its existing configuration.
3. **Retrieve and verify.** Pull or read only the resolved artifacts. Compare their digests or checksums with the producer record, trusted repository metadata, or an explicit immutable reference supplied by the user. If an artifact is missing, its identity is uncertain, or the project has no way to consume it locally, report the specific gap. A missing build belongs to the project's artifact delivery workflow when separately authorized.
4. **Deploy without rebuilding.** Show the user the chosen artifact, local target, command, and evidence before updating the deployment. Execute the supported build-free command. Preserve the project's normal startup checks and any migration gates in that command.
5. **Verify the running result.** Check service health and compare the deployed artifact identities with the resolved inputs using the runtime's inspect or application version mechanism. A successful launch alone leaves identity unverified. Report the selected build or version, immutable references, local target, actual command results and durations, and any unverified checks.

## Docker Compose

Use the project's image variables or a temporary local override when an existing Compose file already defines the local services. Assign each affected service its verified image reference, including startup or migration jobs that use the release images. Preserve other Compose settings and project resources. Inspect the resolved configuration with `docker compose config`, confirm the project name and service image references, and avoid printing environment values or credentials.

Use the effective Compose configuration to pull the selected images and run `docker compose up -d --no-build`, or use an equivalent documented wrapper. Verify service state and compare each container's image ID with the ID resolved locally for its expected digest. Match the same platform when inspecting a multi-platform image. For one-shot jobs, verify the expected exit state as well as the image.
