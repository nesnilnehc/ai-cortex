# Source and Account Binding

Resolve the target before authenticated access. This is working context for one inspection, not a new persistent configuration format. Reuse project conventions and existing verified bindings; save nothing unless requested. Retain only non-secret references in working notes.

## Discover a coherent target

1. Start with explicit user selections, then current project artifact/release configuration, then package metadata and static pipeline settings. Historical notes are leads to recheck. Read only relevant configuration fields; never dump complete client settings or environment variables. Do not execute configuration scripts, project plugins, credential-bearing shell substitutions, or builds to resolve values.
2. Identify the artifact ecosystem and coordinates, repository instance identity, environment/tenant if relevant, and concrete endpoint/repository path. Record which configuration supplied each value. Keep the UI homepage, publication endpoint, consumer endpoint, API service index and storage prefix distinct. Repository aliases are scoped to their configuration; the same alias in another project is not the same instance. Endpoint authority includes scheme, host, port and repository path, not merely a matching hostname.
3. Check explicit values against the remaining configuration. An explicit endpoint overrides an inferred address, but credentials inferred for the old address do not move with it. Conflicting explicit instance/address/account values need clarification. If only some artifacts have a clear target, inspect those while reporting the unresolved selection. Never invent a default environment or use a public client default as evidence of the publication source.
4. Resolve an existing access profile for this exact binding. Prefer an explicitly selected account/profile; otherwise use the project's documented instance-to-account mapping or an already configured connector/client profile whose target matches. A connected tool must support both the desired read operation and this instance; a tool name, visible login or successful access to another repository is insufficient. Use configured anonymous access where applicable. Several eligible profiles with no selection policy require asking which to use, not trying them in turn.
5. Use a narrow authorized metadata read to check the selected target and capability. Retain the chosen profile/reference and whether the authenticated principal is known. Token-only or opaque connector access can remain usable with principal identity unverified when no particular account is required; do not infer the username from the local OS account. If an account is explicitly required, unresolved identity is a gap to resolve. Authentication success alone neither proves visibility of all packages nor that access privileges are read-only; constrain this skill's operations to reads.

Keep each artifact's coordinates, instance, effective endpoint/role and selected access reference together throughout the inspection. For several endpoints, report observations separately. A proxy or virtual repository's response establishes visibility there, not presence in a particular hosted member or upstream. Multiple protocols on the same manager may use different repository paths and different credentials. Do not infer shared access from the common hostname.

## Reuse existing credentials

Let an existing connector, credential provider or native client supply the secret whenever possible. Locate credentials by their established source/profile mapping; do not enumerate a whole secret store looking for plausible passwords. A known environment-variable name, vault reference or keychain reference is a pointer, not a value to echo. Use an existing secure credential channel that scopes the credential to the selected destination and keeps values out of model-visible outputs, command arguments, logs and reports. If the available tool cannot do that, stop that authenticated operation and name the capability needed. Do not fetch secrets merely to test that they exist.

| Ecosystem | Locate and bind existing access |
| --- | --- |
| npm | Resolve the package scope and selected registry using project/client configuration. Let npm use its existing registry-scoped auth settings; check host and any configured path scope against the chosen endpoint. Do not copy a token to another registry or run `npm config list` to expose settings. |
| Maven | Read the selected repository ID/URL and applicable mirror mapping. Native credentials are selected by the effective repository or mirror ID in `settings.xml`; that ID is not the account name. Verify its endpoint binding as well. A mirror credential does not authorize querying the original hosted repository. An HTTP tool cannot automatically consume Maven's encrypted password/provider settings; use a compatible existing client/provider or report the gap. |
| NuGet | Resolve the selected source name/URL and any package-source mapping in effective NuGet configuration. Reuse the corresponding source credentials, configured environment reference or installed credential provider through a compatible tool. A push API key does not by itself establish package read authentication. |
| Python index | Distinguish the installation index from the upload target in publishing configuration. Use only the selected index and its existing host-bound client, netrc or keyring/provider access. An upload token is not automatically a read credential; do not merge all configured extra indexes into the selected inventory. |
| OCI | Bind the explicit registry authority, repository namespace and selected tag/digest to the existing registry auth profile/credential helper. Use a registry-aware read client that actually supports that auth store. Do not assume an arbitrary HTTP tool inherits Docker credentials or that a daemon context identifies the intended registry. |
| Directory/object storage | Bind the selected root or bucket/prefix and environment to an existing filesystem, storage connector, cloud profile or remote-access profile. An accessible mount is evidence of that directory only; do not search unrelated mounts, buckets or accounts. |

Do not create accounts, log in interactively, run credential setup, store/rotate credentials, edit client config, widen permissions, or create a new binding file under this skill. Missing access should lead to a request for an existing profile/reference or separately authorized setup, never a request to paste a secret into the report. Existing broader credentials may be used only for the authorized reads; do not request an elevated account just to overcome an error.

Never put secrets into URLs or reports, disable TLS verification, or forward credentials automatically to a redirected host, a different repository path, or a token-service URL received from an untrusted response. Validate protocol-advertised API/download/auth destinations against the selected service's known trust configuration before credential use. Separate public/CDN reads from authenticated repository access; rebind access for any different destination. Protocol-required temporary tokens must stay scoped to the selected service/repository and read operation, using an existing trusted provider.

## Fail without changing the target

Network/TLS failure, 401, 403, missing profile, unavailable provider or unresolved account selection makes that observation unverified. Do not retry with other accounts, fall back to anonymous access after selected-account failure, switch instances, broaden the root, or interpret a masked 404 as absence. Establish adequate visibility of the selected package/source before confirming absence; preserve listing and pagination limits. Report the affected instance and operation, the non-secret access-profile reference if useful, and the smallest next step. Keep independent accessible sources moving.
