# Existing-project first alignment

Fictional completed adoption example. Compare [before](before/plan.md) and
[after](after/plan.md); these are retained teaching snapshots of the same logical
`plan.md` location, not two active plans. Existing project URLs and source IDs stay
unchanged. There is no strategic-goals file and no independent priority policy.
Neither is automatically created to perform alignment.

## Authorized scope and route

The owner asks for structural alignment only, retaining all existing business
decisions and links. The orchestrator selects `align-existing` before refresh or
intake: review-roadmap → define-roadmap (alignment) → review-roadmap. Strategy
creation, intake, scoring, dependency registration, promotion and archiving are
skipped as out of scope. No default P0→Now mapping is reapplied.

## Review and repair

Before: missing explicit outcomes, a buried delivery commitment, no adoption
baseline, and an execution mapping gap for R2. Structural repair adds sourced
outcomes, separates the overview/arrangement/delivery/basis, preserves old anchors
and surfaces unknown execution before the table. It does not classify R2 as Not
started from its Draft approval. The optional generator is not used: its reserved
`roadmap.md` output would not preserve this project's `plan.md` and existing anchors.

After: known plan facts and links agree with the
[source evidence](sources.md). Missing strategy/policy and R2 execution evidence
remain limitations; no full governance pass is claimed. Adoption baseline is
2026-10-21, with earlier history unknown. The change is structural, so no invented
business revision is added. A repeat alignment produces no additional change.

## Boundary cases

| Request and evidence | Route |
| --- | --- |
| First alignment; structure needs repair; no goals file | Review → define in alignment mode → review; report missing goals |
| First alignment; structure already adequate; execution unknown | Review only; no-write report retains the unknown |
| Align, and separately apply a verified date correction | Review → define if needed → update for that authorized correction → review; other facts preserved |
| Diagnosis suggests promoting a P0 from Next | Report separate proposal; no promotion without that authorization |
| No roadmap found at conventional filename | Discover established location first; if still unavailable, report location gap, not bootstrap |
| Existing requirement body also needs alignment | Requirement review/repair owns draft fixes; frozen originals stay intact, no recapture or priority reset |

The executable example checks compare known facts/order/links and inject drift to
prove detection. They validate this teaching artifact, not execution of a live
agent's intent classification or remote platform editing. See the
[capability guide](../../../../docs/guides/roadmap-planning-usage.md).
